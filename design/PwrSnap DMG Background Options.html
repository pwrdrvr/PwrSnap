Same instinct as the pill, one size up: the pill becomes the panel and the whole install gesture — wordmark, arrow, both icons — happens inside one shape. Nothing is bolted on. The geometry is tight rather than generous, and it has to be: the generator pins the icon row at iconY 230, so the icons occupy 174–286 and the Finder labels start at 292. The card therefore ends at 288 — icons flush to its bottom edge, labels immediately below on the light page, where they stay readable in both appearance modes. Loosening that would mean moving iconY in both the generator and electron-builder.yml.

The tradeoff, which you'll see straight away: the app-icon tile is itself a near-black gradient (#1c1813 → #0c0b09), so on a #0a0a0a card its silhouette nearly vanishes — the orange mark floats and the tile edge barely reads. The folder icon is unaffected. If that bothers you, F needs the card lightened until the tile separates, which starts pulling the wordmark's surround away from the titlebar match — the thing we came here to fix. The other way out of the contrast problem: stop asking the orange to work on white. The arrow is wayfinding, not brand — it becomes #737373, the grey already used for the “Drag to Applications” hint directly beneath it, so the two read as one instruction. Brand orange then appears exactly once, on the near-black pill, where it looks like itself.

Two constants, no geometry, no new values: pillBackground → #0a0a0a, arrowShaft and the arrowhead → the existing instruction grey. Quieter than today's DMG, and closer to how macOS installers usually look.

Retracting the amber arrow I proposed last round. I suggested #e8743a for the arrow on the grounds that it was the suite's value for reading against a lighter field. I made that rationale up. Having now read docs/solutions/2026-05-31-brand-oranges-and-app-icon.md, the actual rule is the opposite: #e8743a is “the macOS app icon only … Nothing else”, its real context is the icon's near-black gradient tile, and the doc closes with “don't unify the icon to #ff8a1f or the wordmark to #e8743a.” It also states plainly that the DMG wordmark and arrow are #ff8a1f.

So options C and C′ as I first drew them (both now withdrawn — see F and G above) would have put a third usage on a pinned token — the same class of mistake as the doc line recording PwrAgent's DMG bug as a decision. Both are corrected below to keep #ff8a1f. If you ever do want the amber on the arrow, that's a real brand call needing sign-off, not something this page should present as precedent.

Every orange pixel now sits on the same near-black as the app. The pill has nothing left to do once the page is dark, so it goes. But look at the two icon labels — see the warning below.

The catch, and it's a real one: the icon labels under “PwrSnap” and “Applications” are drawn by Finder, not by this PNG. Finder colours them by the user's appearance setting — near-black in Light Mode, white in Dark Mode — and the background image is fixed either way. A near-black background means every Light Mode user gets black labels on black. That is almost certainly why this DMG was built light in the first place.

Option B is only safe if you're willing to have the labels effectively vanish for Light Mode users. I would not ship it.
